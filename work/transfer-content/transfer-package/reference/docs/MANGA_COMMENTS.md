# Manga discussion — Phase 4.6B

## Contract

`MangaComment` belongs directly to a Manga, not to Community content or Review.
Only `PUBLIC` non-`ADULT` Manga is eligible, using the same predicate as the catalog/detail API.
Guests can read. An eligible ACTIVE session can create, reply, edit or remove its own content.
Bodies are trimmed plain text, 1–5000 semantic characters; spoiler is an explicit boolean.
The client never supplies actor, state or timestamps. Replies have one level, to a PUBLISHED root in the same Manga.

Creation produces PUBLISHED. Editing is owner-only/PUBLISHED and requires an effective change.
Author removal changes PUBLISHED or HIDDEN to REMOVED immediately and permanently.
`moderate.manga_comments` permits PUBLISHED → HIDDEN and HIDDEN → PUBLISHED, with a required trimmed reason (1–2000).
Repeated transitions return 409. REMOVED cannot be edited or restored.
Hiding/removing a root preserves its children and their independent states.

Public HIDDEN/REMOVED projection contains a null body, false spoiler and null editedAt.
There is no public original body, reason, moderator identity or private author ID.
Author projection contains only username, displayName and safe avatar representation.
Spoiler text is not rendered in the DOM until the reader reveals it.

## API/cache boundaries

| Route | Authority | Result |
| --- | --- | --- |
| GET `/manga/:slug/comments` | Public | Roots with up to five initial replies each |
| GET `/manga-comments/:commentId/replies` | Public | Replies, independent cursor |
| POST `/manga/:slug/comments` | Session/Origin/CSRF/ACTIVE/rate limit | 201, canonical comment |
| PATCH `/manga-comments/:commentId` | Same; owner | 200, canonical comment |
| POST `/manga-comments/:commentId/remove` | Session/Origin/CSRF/ACTIVE/owner | 200, removed projection |
| POST `/manga-comments/:commentId/hide` or `/unhide` | Session/Origin/CSRF/global permission | 200, canonical public projection |
| GET `/me/manga-comments/access` | Session | canParticipate, canModerate only |
| POST `/me/manga/:slug/comment-ownership` | Session/Origin/CSRF | Current user's owned IDs, maximum 300 input IDs |

Public reads use `no-store`, omit credentials in the Web transport and never contain viewer capabilities.
Private reads and mutations use `private, no-store`. Core Manga caching is unchanged.
Ownership uses a bounded private batch, not username comparisons or one request per comment.
Web mutations consume the server's final projection to update only the affected discussion; there is no full-page refresh or automatic write retry.
Manga/session changes remount the discussion and abort its reads. Old writes cannot update the new scope.

## Query/concurrency

Roots use `(createdAt DESC, id DESC)`; replies use ASC. Page size defaults to 20, maximum 50.
Cursors are bounded, opaque, versioned, scoped to Manga/parent and independent of cursor-row existence.
The initial list makes a Manga gate, a bounded roots call, one parameterized LATERAL batch (six candidates/root, five exposed) and a PUBLISHED-only count including replies.
The UI labels that count explicitly as published comments including replies, not all placeholders.
There is no application N+1. Prisma may execute additional SQL for nested author relations; this is not a claim of a single SQL statement.

Interactive Read Committed transactions lock/revalidate Manga with FOR SHARE, then target/parent with FOR UPDATE.
Ownership/state is reread after the lock; writes are conditional. Moderation transition, ModerationAction and final projection share one transaction.
No external I/O occurs while holding locks. Nine coordinated PostgreSQL races exercise real HTTP/service paths and assert committed state/audit correlation.

## Migration/deployment

025 is additive: MangaCommentStatus, MangaComment, MANGA_COMMENT moderation target, checks, indexes and RESTRICT FKs.
UUIDv7 IDs and updatedAt are generated by Prisma; createdAt has a DB default.
The composite parent FK prevents cross-Manga relations. SQL also rejects bodies blank after ECMAScript trim whitespace (including tabs/NBSP/BOM), self-parent and inconsistent REMOVED/deletedAt.
Reply depth and current parent eligibility are enforced under application locks.
No legacy backfill, reinterpretation or destructive cascade. Migrations 001–024 are unchanged.

Deploy migrations using the database owner/migration role: adding an enum value requires ownership of the existing enum.
The runtime/test-runner role should not be elevated to a migration owner. Grant the existing runtime role its normal CRUD privileges on the new table if deployment does not already set default privileges.
An isolated PostgreSQL schema replay of 001–025 verifies a nonempty 024 upgrade and preservation of preexisting Manga/User rows, then rolls back the verification schema.
Development DB migration/provisioning is a separate operational action and is not run automatically by this implementation.

The existing idempotent `provisionGlobalAuthorizationCatalog` is reused. Previously its only entry point was the demo seed, so a catalog-only CLI was added; it creates/updates only Role, Permission and ADMIN RolePermission catalog rows in one transaction, never users or content.
With the intended DATABASE_URL selected explicitly, run from `apps/api`:

```text
pnpm build
node dist/src/authorization/provision-global-authorization-catalog.cli.js
```

Do not use the demo seed to provision a production permission. Bare MODERATOR receives no automatic manga-comment authority. Existing ADMIN resolution semantics remain unchanged; the catalog also maps ADMIN's moderation capability consistently with existing permissions.
The direct-grant UI now recognizes the new key. Granting/revoking still uses the existing audited admin workflow.

## Rate limit / scope

Create+reply share 5/minute and 50/hour per account. Edit has its own 10/minute bucket.
429 includes Retry-After. The existing storage is process-local memory: P3 operational limitation for multi-process deployments; limits are not distributed or durable across restarts.
No Redis/dependency added. No reactions, report workflow, notifications, attachments, Chapter comments, Reader/progress change or editorial lifecycle change.
